# 项目设计原则

### IM 斜杠命令扁平化

内容：IM 里的斜杠命令不用"命令 + 子命令"的层级结构（如 `/schedule run`）。命令就是命令，需要复合语义时用横杠连接成一个词（如 `/schedule-run`、`/schedule-bind`），解析简单、意图明确。

适用场景：所有 IM 侧（飞书/企微/微信）斜杠命令的设计。

### 用超时兜底替代并发状态机

内容：对"任务/作业"类功能，不为并发冲突引入配置项（如 overlap: skip/queue/restart）。改为每个任务声明最大执行超时，生命周期只有两个终态：完成或超时。每次触发都是全新的独立执行，靠隔离性而非互斥策略保证正确性。

适用场景：定时任务、后台作业等"触发-执行-结束"型功能。前提是每次执行完全独立、无共享状态。

### 任务会话隔离，只借用投递能力

内容：由 bridge 主动发起的工作（如定时任务）必须运行在独立的临时会话中，绝不触碰用户聊天的会话绑定；只在最后把结果通过 Client Adapter 的正常投递管线发到指定聊天。

适用场景：任何 bridge 侧主动触发、需要把结果推送到 IM 会话的功能。

### 低频管理操作交给 AI 编辑文件，不加 IM 命令

内容：不为低频管理操作（如定时任务解绑）增加 IM 斜杠命令；用户可以直接让 agent 编辑对应文件，靠热加载生效。IM 命令只保留高频、对话中自然发生的操作（如 `/schedule-here` 绑定）。

适用场景：bridge 功能的管理/配置类操作设计。前提是操作对象有明确、可编辑的文件载体且热加载可靠。

### 单人项目不做兼容性设施

内容：本项目仅作者本人使用，破坏性变更直接做：不为旧数据格式/旧目录布局写迁移逻辑、兼容扫描或 deprecation warn。升级后失效的东西由作者手动处理或让 AI 排查。

适用场景：数据迁移、旧格式兼容、breaking change 提示等决策。例外：如果项目未来有其他用户，此原则需重新评估。

### bridge 不复制 adapter 的会话记录职责

内容：忠实记录完整会话（tool call、thinking、SubAgent）是 agent adapter 的职责且它已做好（如 pi session file）。bridge 侧的功能性文件（如 Output File）只记 bridge 自己产生的增量信息（对用户说了什么），需要细节时用 agentSessionId 桥接到 adapter 的存储，绝不重复造一份。

适用场景：bridge 内任何"留痕/日志/转录"类设计。

### 持久化按模块分文件，不合并

内容：不同功能模块的持久化数据各自成文件（如 schedule.jsonl / queue.jsonl），即使结构当前相同也不合并成一个。模块演进自由、查询入口本来也按模块分。

适用场景：多模块同构数据的存储设计。
